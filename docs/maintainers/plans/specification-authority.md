# One authoritative specification per subject

This plan records the transition to one authoritative specification per subject. To migrate an older project, follow [Move an inline declaration](#move-an-inline-declaration). Each valid authored `*.spec.md` file specifies one primary subject. A reusable quality model is independently authored reference material in a `*.quality-model.md` file. [What belongs in a specification?](../../cli-handbook/explanations/what-belongs-in-a-specification.md) Each specification kind has one declaration form. A requirement is declared in a `*.requirement.spec.md` file. The product specification brings those sources together through links and generated views. The [contributor guide](../../../CONTRIBUTING.md#specification-tests-and-implementation-tests) governs this convention.

## What each source owns

The [Markdown mapping](../../../model/markdown-mapping.md) identifies how authors declare specifications and their parts.

An action belongs to its concept, a step to its use case, a criterion to its requirement, and a named concept use to its declaring system or component. Each can have a heading, an ID, links, and a generated report or passage. Its owner remains the place to edit it. Keep existing identity and scoping rules. Equal titles across scopes are insufficient evidence of duplicate authorship. The current model already tests the correspondence between document roots and concrete specification classes. [Specification type tests](../../../internal/model/specification_types_test.go)

External policies and native contracts retain authority over their own provisions. A dotspec subject can cite an exact provision and state how it applies. An executable check owns its inputs, assertions and observations. Where this repository currently treats a test assertion as the sole definition of required product behavior, identify the governing spec or author the missing requirement before changing the test’s designation. Preserve links to the executable examples. The system policy and contributing guide define these roles. [Test roles](../../../CONTRIBUTING.md#specification-tests-and-implementation-tests)

## How use cases relate to requirements

An essential use case identifies an interaction the system must support. During elicitation, walk through the interaction to discover needed functions, properties and assumptions. During requirements verification, walk through it again and ask, **could an implementation satisfy the written specifications and still prevent the actor from completing this step?** Review the main path, extensions, and guarantees. Follow the specifications for the relevant concept actions, business rules, interfaces and requirements. A gap can call for a better action definition, a corrected precondition, or a new general requirement.

This is Meyer's scenario-completeness test. One scenario can exercise several specifications, and several scenarios can exercise the same requirement. Passing an acceptance test supplies evidence for the exercised conditions. Deciding whether the specified functionality covers the identified scenarios requires review. A universal link-per-step check would measure a different property. See Bertrand Meyer, *Handbook of Requirements and Business Analysis* (2022), §§7.4–7.6, pp. 133–136, and §11.3, p. 207. [Book](https://doi.org/10.1007/978-3-031-06739-6)

Keep the existing relationship meanings. A step’s **Illustrates** link identifies the requirement, business rule or concept action it demonstrates. **Refines** identifies a more precise statement that preserves the parent commitment. **Derived from** records a basis. **Applies to** records an explicit target. Each forward declaration lives at its source and supplies reverse navigation. Ordinary Markdown citations stay available wherever they help. A scenario, a shared title, and directory placement each provide insufficient grounds to infer refinement. [Relationship contract](../../../model/markdown-mapping.md#relationship-contract)

## Move an inline declaration

Work in a project with the current CLI. Start at the source location reported by `structure.inline-requirement`. Read the text under the old heading and look for incoming links to that file and fragment. Decide which claim those readers need to reach.

- If the text describes what happens on one path, put the outcome in the use case's scenario, extension or guarantees. Update readers' links to that passage.
- If it promises something the system must do whenever stated conditions hold, find the requirement that owns that promise. If it needs a new home, create a requirement from the owning directory, move the statement, conditions and criterion together, and link to its source. A scenario step can link to it under **Illustrates**. A feature can include it under **Groups**. Use the relationship that describes what each reader needs. [Write an assessable requirement](../../cli-handbook/guides/write-an-assessable-requirement.md) · [Write a use case](../../cli-handbook/guides/write-a-use-case.md).

Replace links to the retired fragment, then remove the old declaration heading. Read the changed use case through each ending. A reader should still be able to tell what happened to the actor and follow any independent promise to the place that governs it.

From the directory containing the project's `dotspec.yaml`, run `dotspec model trace` and inspect which steps illustrate the requirement. For a project with reports enabled, run `dotspec spec build` and open the requirement from the affected scenario and feature, where applicable. Follow the report's `source` back to the editable file. Run `dotspec check` from that directory. For an unresolved fragment, inspect the reported source link and its destination heading, repair it in the authored file, then rebuild and check again. [Build and inspect the reports](../../reference/generated-specification.md).

## Worked migration for the personal task list

In *Decide what to do about a waiting errand*, the owner returns to a waiting repair and takes up the work when the plumber asks for a photo. The list shows the same repair in Open. *Preserve tasks across restart* specifies what survives after acknowledgement when the service restarts on the same database, including what happens to deleted entries. A test could find the repair after a restart by matching its title while overlooking that the service had assigned it a new identity. That test would miss a violation of the restart requirement. The acceptance test compares identities as well as the visible list state. [Use case](../../../examples/todo/specs/use-cases/resume-list.use-case.spec.md) · [Restart requirement](../../../examples/todo/specs/requirements/restart.requirement.spec.md) · [Acceptance test](../../../examples/todo/tests/acceptance.py)

**Decision.** Returning to the same local database has its own [availability requirement](../../../examples/todo/specs/requirements/availability.requirement.spec.md). The return step illustrates it. The restart requirement refines it by specifying which data survives an acknowledged change followed by a restart.

## Implementation sequence

The following sequence records the implementation decisions and the evidence requested at each stage.

| --- | --- | --- |
| 1. Establish authority and vocabulary | Update the system policy and authoring guidance. For each supported spec kind, identify its primary subject, named parts, and permitted references. Inventory formal inline declarations, incoming links, affected test assertions and public examples. Preserve the agreed todo availability requirement. | A maintainer can identify the editable source for a use-case outcome, a concept action, an external provision and a product requirement. Existing requirements expressed only in tests have a disposition. |
| 2. Simplify the metamodel | Keep `Requirement` as a concrete `SystemContextSpecification`. Move the statement, applicability, explicit targets, rationale, refinement, quality classification and optional criterion onto it. Use `RequirementCriterion` for the structured criterion. Preserve narrative, examples, links, optional fields, and source spans. ### Overview policy

Use the section map for the complete **business rules**, **use cases**, **requirements**, **concept definitions**, and **jobs** indexes. Keep authored stakeholder needs and contextual links in Purpose and Scope. Show capabilities beside their providers under **Architecture** and link the full capability index. Keep named concept uses and synchronizations when they explain this system’s behavior. Keep features, goals, system-wide assumptions and constraints, immediate parts and boundary interactions, and the system’s full quality attribute hierarchy in the body. Keep each attribute’s classified requirements on its linked report. Apply the same conventions to component overviews where relevant, preserving component responsibilities and contracts.

Choose placement by the reader’s task and collection role, independent of the number of entries. Within a body section that introduces a collection, show all applicable substantive entries in index order. Preserve the established labels and canonical destinations across overviews, indexes and subject pages.

## Acceptance and release

Use these cases when reviewing a change to specification ownership. Work from the root of a dotspec checkout with the [contributor tools](../../../CONTRIBUTING.md) installed. Make the source and generated-file mutations in a disposable copy. The To-do project covers all supported specification types. From the checkout root, `go run . model export --project todo` reads that fixture. From `examples/todo/`, an installed `dotspec` selects it directly.

1. Export a fixture covering all supported spec types. Each valid spec file declares one primary subject of its declared type. Named parts resolve to their owning source and heading. The requirements collection consists entirely of requirement-file roots.
2. Reference one requirement from two use cases and one feature. Export one requirement, preserve all authored references, and resolve every typed relationship to the intended endpoint. Edit its statement once and rebuild. Every generated summary reflects the change and points back to that file.
3. Check a legacy inline declaration in each formerly supported container. Expect a located error and no inline requirement record. Check ordinary outcome prose, a named scenario step, and an example code block containing the same heading text. Expect the prose and addresses to survive. Reject a forged snapshot containing a retired record or endpoint under the new schema.
4. Review the migrated todo scenario against its specifications step by step. Record what supports finding the completed entry, preserving its identity and reopening it, and what supports the deleted-entry extension. From the checkout root, run `python examples/todo/tests/acceptance.py` to exercise the application against a temporary database. A passing restart test and a successful scenario review answer different questions.
5. Compare the generated todo and dotspec reports. An index-only category has a working section-map link for one or many members. A contextual reference opens the exact subject or passage. Empty collections stay absent. Editing a generated statement or breaking a required link triggers a check finding.
6. Run `mise run model-generate`, `mise run model-test`, and `mise run model-check`. Run `mise run generate` and `mise run check`, including project-wide specification checks and the todo reader journey. Repeat generation and verify zero drift. Document the breaking format change and the two migration choices for existing inline declarations. [Model workflow](../../../model/README.md) · [Repository checks](../../../mise.toml)
