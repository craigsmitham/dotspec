# Components and their responsibilities

A part of a system warrants its own specification when it matters **which part is responsible**. A person using To-do wants to see the same tasks on returning to the list. A developer changing the browser needs a more specific answer. When the service reports success, can the browser tell the person it is safe to close the list?

The **Task service** accepts changes from the browser and stores them locally. It is the part that knows whether a change has been committed. If the service replied before committing, the person could see a successful save and still lose it on an immediate restart. This is why the confirmation requirement applies specifically to Task service. Its component page describes the responsibility and points to the Task list forms contract. The requirement states the order that a new implementation must preserve. [Task service](../../../examples/todo/app/specs/task-service.component.spec.md#responsibilities) · [Acknowledge after commit](../../../examples/todo/app/specs/requirements/acknowledge-after-commit.requirement.spec.md#statement).

Meyer's *Handbook of Requirements and Business Analysis* distinguishes the parts a system contains from the responsibilities assigned to them and the interfaces through which others obtain service. In dotspec a component explicitly names one parent system or component in **Part of**. That makes the architecture readable even when a team moves code between directories. Interacting with another service also gives a team reason to describe the interface between them. Calling that service tells us who participates in the exchange. To call it a component of this system, we still need to know that it belongs inside the system boundary. [Meyer (2022), §§1.8.1–1.8.2 and 3.6, S.1–S.3](https://doi.org/10.1007/978-3-031-06739-6) · [Task service’s declared parent](../../../examples/todo/app/specs/task-service.component.spec.md#part-of).
