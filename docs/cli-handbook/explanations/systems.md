# Systems and their boundaries

If a task disappears after a restart, has the personal task list failed? That depends on what happened to the list. A system boundary identifies the subject whose behavior the team is specifying. The environment includes the people, systems and conditions outside that boundary that affect the result.

The To-do system exists to help one person resume unfinished work on one computer. The person may stop the service between sessions. If they restart it on the same functioning database, the service owes them every entry they kept, with the details of its last acknowledged state, including any reply they were waiting for. Entries they deleted must stay absent. Loss of the database file is a different case. The person still wants their list back, but the system expressly excludes that recovery and assumes the same local storage will be available. The purpose explains why both cases matter. The scope, exclusion and assumption explain why only one falls under the restart requirement. [Personal task list](../../../examples/todo/specs/personal-task-list.system.spec.md#scope) · [Preserve tasks across restart](../../../examples/todo/specs/requirements/restart.requirement.spec.md#statement).

Bertrand Meyer distinguishes properties the project can decide from conditions the world imposes on it. dotspec lets an author record both in the system specification so a reader can see what a promise depends on. If the team undertook to restore tasks after disk loss, access to the old file would no longer suffice as an assumption for that promise. The team would have to explain where the recoverable copy comes from and what loss it can survive. Silence about disk loss would leave the question open. [Meyer, *Handbook of Requirements and Business Analysis* (2022), §§1.1.1–1.1.2, 1.7.3](https://doi.org/10.1007/978-3-031-06739-6).
