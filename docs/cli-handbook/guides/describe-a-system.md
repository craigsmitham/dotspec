# Describe a system and its boundary

Choose a situation the system is meant to handle and one close enough that a stakeholder might expect it too. Find out who depends on the result and which part of it the team has agreed to deliver.

In the directory that will own the system, edit its existing `*.system.spec.md` file. For a new system, run `dotspec system init "Personal task list"`, substituting your system’s name. The name in the top-level heading determines the filename.

Fill in **Description**, **Purpose** and **Scope**. Say what the system is, whom it helps and which work it covers. For the personal task list, “pick up unfinished work” explains the benefit. “One person’s commitments on one computer” bounds the work. If the team has agreed to exclude a plausible case, put that decision under **Out of scope**. If the team still needs to decide, record the question under **Framing**. [Personal task list](../../../examples/todo/specs/personal-task-list.system.spec.md#scope).

Under **Goals**, give each benefit stakeholders expect its own level-three heading and say what should improve. In Meyer’s Standard Plan, expected benefits are the core of the Goals book and help keep a project focused. A job that serves the goal links to it under a level-two **Supports** heading, and its outcomes say what to observe. In To-do, the commitments job supports *Resume unfinished work*, and its outcome *Less reconstruction* concerns the time to find the next action after an interruption. [Meyer, *Handbook of Requirements and Business Analysis* (2022), §3.4, G.3](https://se.inf.ethz.ch/requirements/plan.pdf) · [Personal task list goals](../../../examples/todo/specs/personal-task-list.system.spec.md#goals) · [Less reconstruction](../../../examples/todo/specs/jobs/personal-commitments.job.spec.md#less-reconstruction).

Ask what the system must handle and what it can count on. Meyer uses the same screen sizes to show the difference. A team can promise to support every size in a range. It can also assume that everyone who uses the system has a screen within that range. A screen outside the range challenges the assumption. A display failure inside the range challenges the promise. [Meyer, *Handbook of Requirements and Business Analysis* (2022), §3.5, E.3–E.4](https://se.inf.ethz.ch/requirements/plan.pdf).

In dotspec, describe the setting under **Environment**. Give a condition the system counts on a named level-three heading under **Assumptions**, so the requirement that depends on it can link there. In To-do the owner may stop the service between visits. The restart requirement promises recovery and links to the assumption that the owner returns to the same writable database. Under the assumption, add level-four **Basis** and **Applicability** headings that say why relying on it is justified and where it holds. From the project root, `dotspec model pegs` flags an assumption that lacks either. Likewise, the local day may change between visits. What the owner should see on the new day belongs in the follow-up requirement. [Personal task list environment](../../../examples/todo/specs/personal-task-list.system.spec.md#environment) · [Same local storage](../../../examples/todo/specs/personal-task-list.system.spec.md#same-local-storage) · [Restart requirement](../../../examples/todo/specs/requirements/restart.requirement.spec.md#relies-on) · [Follow-up requirement](../../../examples/todo/specs/requirements/follow-up.requirement.spec.md#statement).

From the system directory, run `dotspec system show` and check the displayed purpose, scope and source path. Read the exclusions and assumptions in that file. Can a stakeholder explain what to expect in both of your situations? If their answer turns on an unstated condition, add it to the declaration and try the cases again.
