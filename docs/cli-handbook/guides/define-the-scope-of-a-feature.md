# Define the scope of a feature

Choose a stakeholder and a benefit they would recognize. Which product behaviors have to work together to deliver it? Ask someone returning to To-do what “pick up where I left off” entails. Finding the errand and recovering its last saved state both matter. A count of all open errands answers a different question about workload. This use of stakeholder value as the grouping criterion follows IREB. [IREB, *Glossary of Requirements Engineering Terminology*, v2.2.0, “Feature”](https://cpre.ireb.org/en/downloads-and-resources/glossary?first-letter=F&tag=cpre-glossary).

From the owning system or component directory, run `dotspec new feature resume-work`, using a lowercase, hyphenated name for your feature. If a declaration already exists, edit that `*.feature.spec.md` file. Give the feature its stakeholder-facing name in the top-level heading. Describe the available behavior under **Description** and its benefit under **Purpose**. When the members only make sense together, explain how they combine under **Overview**. Someone returning to To-do relies on recovery after a restart to find yesterday’s errand and on the follow-up cue to know it is time to chase the reply. Leave each promise to the specification that states it.

Under a level-two **Groups** heading, link to each specification that describes part of the behavior. In To-do the owner decides what to do about a waiting errand. Which promise lets them see that a call needs chasing today? Which lets them find the errand when they come back, even after a restart? Link to the return use case, the follow-up requirement, the availability requirement and the restart requirement that refines it. A feature can also group a concept, a named concept use, a synchronization or an interface. Another feature that depends on the same guarantee can link to the same requirement. Keep the statement, conditions and criteria there. [Worked feature](../../../examples/todo/specs/features/pick-up-where-i-left-off.feature.spec.md#groups).

From the project root, run `dotspec build` and open your feature’s report in `specification/features/`. Its **Groups** section lists each member. If a member is missing, check its target and the **Groups** heading in the feature file, then rebuild. For each listed member, ask what would go unexplained if you removed it. If the only connection is a shared screen or team, remove that membership and check the scope again. Then look for omissions. Follow each grouped use case to its report, where every step lists what it **Illustrates**. When a grouped use case illustrates a requirement the feature does not list, ask whether the benefit depends on it directly or through a listed member. To-do’s failed-save extension illustrates *Acknowledge after commit*. The feature leaves that Task service commitment to the restart requirement it is derived from. [What holds a feature together?](../explanations/features.md).

Once the group is settled, try a case that makes two members apply at once. Can the system deliver the benefit while honoring both promises? [Review a set of requirements](review-a-set-of-requirements.md).
