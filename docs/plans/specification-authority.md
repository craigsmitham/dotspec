# One authoritative specification per subject

**Implementation plan.** Each valid authored `*.spec.md` file specifies one primary subject. Each specification kind has one declaration form. A requirement is declared in a `*.requirement.spec.md` file. The product specification brings those sources together through links and generated views. The [system source-authority policy](../../specs/dotspec.system.spec.md#source-authority) governs this convention.

## What each source owns

The [authority guide](../handbook/requirements-layers.md#choose-the-authoritative-specification) identifies the editable source for each specification kind.

An action belongs to its concept, a step to its use case, a criterion to its requirement, and a named concept use to its declaring system or component. Each can have a heading, an ID, links, and a generated report or passage. Its owner remains the place to edit it. Keep existing identity and scoping rules. Equal titles across scopes are insufficient evidence of duplicate authorship. The current model already tests the correspondence between document roots and concrete specification classes. [Specification type tests](../../internal/model/specification_types_test.go)

External policies and native contracts retain authority over their own provisions. A dotspec subject can cite an exact provision and state how it applies. An executable check owns its inputs, assertions and observations. Where this repository currently treats a test assertion as the sole definition of required product behavior, identify the governing spec or author the missing requirement before changing the test’s designation. Preserve links to the executable examples. The system policy and contributing guide define these roles. [System policy](../../specs/dotspec.system.spec.md#source-authority) · [Test roles](../../CONTRIBUTING.md#specification-tests-and-implementation-tests)

## How use cases relate to requirements

An essential use case identifies an interaction the system must support. During elicitation, walk through the interaction to discover needed functions, properties and assumptions. During requirements verification, walk through it again and ask, **could an implementation satisfy the written specifications and still prevent the actor from completing this step?** Review the main path, extensions, and guarantees. Follow the specifications for the relevant concept actions, business rules, interfaces and requirements. A gap can call for a better action definition, a corrected precondition, or a new general requirement.

This is Meyer's scenario-completeness test. One scenario can exercise several specifications, and several scenarios can exercise the same requirement. Passing an acceptance test supplies evidence for the exercised conditions. Deciding whether the specified functionality covers the identified scenarios requires review. A universal link-per-step check would measure a different property. See Bertrand Meyer, *Handbook of Requirements and Business Analysis*, §§7.4–7.6, pp. 133–136, and §11.3, p. 207. [Book](https://doi.org/10.1007/978-3-031-06739-6)

Keep the existing relationship meanings. A step’s **Illustrates** link identifies the requirement, business rule or concept action it demonstrates. **Refines** identifies a more precise statement that preserves the parent commitment. **Derived from** records a basis. **Applies to** records an explicit target. Each forward declaration lives at its source and supplies reverse navigation. Ordinary Markdown citations stay available wherever they help. A scenario, a shared title, and directory placement each provide insufficient grounds to infer refinement. [Relationship guide](../handbook/relationships.md)

## Worked migration for the personal task list

In *Return to my list*, a person completes an errand, returns, finds it, and reopens it. The person’s return is explicit. A service restart is absent from the scenario. *Preserve tasks across restart* specifies what survives after acknowledgement when the service restarts on the same database, including what happens to deleted entries. The acceptance test exercises that additional condition. [Use case](../../examples/todo/specs/use-cases/resume-list.use-case.spec.md) · [Restart requirement](../../examples/todo/specs/requirements/restart.requirement.spec.md) · [Acceptance test](../../examples/todo/tests/acceptance.py)

**Decision.** Returning to the same local database has its own [availability requirement](../../examples/todo/specs/requirements/availability.requirement.spec.md). The return step illustrates it. The restart requirement refines it by specifying which data survives an acknowledged change followed by a restart.

### Overview policy

Use the section map for the complete **business rules**, **use cases**, **requirements**, **concept definitions**, and **jobs** indexes. Keep authored stakeholder needs and contextual links in Purpose and Scope. Show capabilities beside their providers in topology and link the full capability index. Keep named concept uses and synchronizations when they explain this system’s behavior. Keep features, goals, system-wide assumptions and constraints, immediate topology, and the system’s top-level quality concerns in the body. Put quality hierarchies and requirement classifications on the linked quality pages. Apply the same conventions to component overviews where relevant, preserving component responsibilities and contracts.

Choose placement by the reader’s task and collection role, independent of the number of entries. Within a body section that introduces a collection, show all applicable substantive entries in index order. Preserve the established labels and canonical destinations across overviews, indexes and subject pages.

## Acceptance and release

1. Export a fixture covering all supported spec types. Each valid spec file declares one primary subject of its declared type. Named parts resolve to their owning source and heading. The requirements collection consists entirely of requirement-file roots.
2. Reference one requirement from two use cases and one feature. Export one requirement, preserve all authored references, and resolve every typed relationship to the intended endpoint. Edit its statement once and rebuild. Every generated summary reflects the change and points back to that file.
3. Check a legacy inline declaration in each formerly supported container. Expect a located error and no inline requirement record. Check ordinary outcome prose, a named scenario step, and an example code block containing the same heading text. Expect the prose and addresses to survive. Reject a forged snapshot containing a retired record or endpoint under the new schema.
4. Review the migrated todo scenario against its specifications step by step. Record what supports finding the completed entry, preserving its identity and reopening it, and what supports the deleted-entry extension. Independently run the restart acceptance test. A passing restart test and a successful scenario review answer different questions.
5. Compare the generated todo and dotspec reports. An index-only category has a working section-map link for one or many members. A contextual reference opens the exact subject or passage. Empty collections stay absent. Editing a generated statement or breaking a required link triggers a check finding.
6. Run `mise run model-generate`, `mise run model-test`, and `mise run model-check`. Run `mise run generate` and `mise run check`, including project-wide specification checks and the todo reader journey. Repeat generation and verify zero drift. Document the breaking format change and the two migration choices for existing inline declarations. [Model workflow](../../model/README.md) · [Repository checks](../../mise.toml)
