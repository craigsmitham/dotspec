# Requirements review example

This fictional workspace illustrates optional requirements-review content inspired by Meyer's handbook: explicit exclusions, required/provided interfaces, environmental premises, actionable questions, an authored effects matrix and terminology review.

Run `dotspec model review --path examples/requirements-review` or `dotspec model pegs --path examples/requirements-review` from the repository root. Use `dotspec model docs` with the same path to render the effects matrix.

The example deliberately leaves one goal without a contribution path, conversational steps without illustration links, one obligation without a verification plan, an interface without a contract, an incomplete question and a glossary collision. These are advisory review prompts. They neither invalidate the draft nor establish defects in an implementation.

The clock service is an interaction partner, not a structural part. Native OpenAPI and project files remain authoritative in their own roles. All observations and responsibilities here are illustrative.

Validation plans illustrate requirements fitness, proposed-concept and use-case fitness,
system intended use, and empirical support plus justified reliance for the clock premise.
They record no completed observations, assessments or acceptance. The feedback quality
requirement deliberately supplies measurement-only guidance without a defined criterion
or operating context, demonstrating advisory measurement-basis findings.
